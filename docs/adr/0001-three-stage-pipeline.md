# ADR-0001: 3段パイプラインの採用

## ステータス

採用済

## コンテキスト

「自撮り写真から最も魂が似ている歴史人物を提示する」という機能を実装するにあたり、LLM の活用方法を設計する必要があった。

最もシンプルな実装は「写真と人物リストを LLM に渡して、似ている人物を選ばせ、理由も生成させる」単段プロンプトだが、これには複数の問題がある。

1. **人気バイアス**: LLM は訓練データに多く登場する有名人（ナポレオン・リンカーン等）を繰り返し返す傾向がある
2. **再現性の欠如**: 同じ写真でも実行ごとに異なる人物を返す可能性があり、デバッグとテストが困難
3. **ハルシネーション境界の不明確さ**: 「誰を選ぶか」と「なぜ似ているか」が混在すると、誤情報がどこで生まれたか追跡できない
4. **テスト不可能**: 人物選定ロジックをコードレビューで検証できない

## 決定

処理を3つの Stage に分離する。

```
Stage 1: extractUserFeatures()   ← Claude Vision + Tool Use
         写真 → 8軸の構造化特徴

Stage 2: scoreFigures()          ← 純関数（LLM 不使用）
         特徴 × 200名データセット → 最高スコア人物

Stage 3: generateNarrative()     ← Claude（別 Tool）
         上位特徴 + 人物 → 理由・エピソード・引用
```

各 Stage は入出力が明確に定義されており、`src/app/api/analyze/route.ts` のエントリポイントが順に呼び出す。

## 理由

- Stage 1 の出力を閉じた enum に制約することで、LLM が「顔の特徴」について嘘をつく余地をなくす
- Stage 2 を純関数にすることで、人物選定が完全に決定論的になり、同じ入力には必ず同じ人物が返る
- Stage 3 は「語り」に特化するため、事実的な誤りのリスクをナラティブ層に閉じ込められる
- 各 Stage を独立してテスト・デバッグできる（`scoring.test.ts` が Stage 2 のみをカバーしている）

## 結果・トレードオフ

**良い点:**
- 人物選定にハルシネーションが構造的に発生しない
- スコアリング重みの調整がコード差分として現れ、レビュー可能
- Stage 2 は 200名全員に対して O(n) で計算し、外部 I/O がないためレイテンシへの影響がない

**トレードオフ:**
- API コールが2回（Stage 1 + Stage 3）になるため、単段よりレイテンシが増加する
- Stage 1 の enum 定義が変わると、データセット側の `features` も合わせて更新が必要

## 検討した代替案

| 案 | 却下理由 |
|----|---------|
| 単段プロンプト（写真 + リスト → 人物 + 理由） | 人気バイアス・再現性・テスト不能の問題が全て残る |
| RAG（ベクトル検索で人物を絞り込んでから LLM） | 特徴の次元数が小さく（8軸）、ベクトル検索の導入コストが不釣り合い |
| 顔認識 API（AWS Rekognition 等）| 有名人との類似判定に特化しており、歴史人物データセットへの適用が困難 |
