# ADR-0003: Stage 2 を純関数にして LLM を排除

## ステータス

採用済

## コンテキスト

200名の歴史人物データセットの中から「最も特徴が近い人物」を選ぶロジックを、どのように実装するかを決定する必要があった。

LLM に「この特徴プロフィールに最も近い歴史人物は誰ですか？」と聞く実装が最も手軽だが、それを選ばなかった理由がある。

## 決定

`scoreFigures()` を副作用なし・外部 I/O なしの純関数として実装した。

```typescript
// src/lib/scoring.ts
export function scoreFigures(
  user: UserFacialProfile,
  figures: readonly HistoricalFigure[],
): { figure: HistoricalFigure; matchRate: number; breakdown: FeatureBreakdownItem[] }
```

アルゴリズム:
1. 8軸の特徴ごとに、ユーザー値と人物値の類似度を類似度行列（例: `FACE_SHAPE_SIMILARITY`）から取得
2. 各軸の重み（現在は全軸 10 点の均等配分）を掛けて加算
3. 強度スコア（`*Intensity`）で表示用スコアを調整
4. 全200名を線形スキャンして最高スコアの人物を返す

## 理由

- **再現性**: 同じ入力に対して必ず同じ人物が返る。ユーザーが「もう一度診断」しても結果がぶれない
- **コストゼロ**: Anthropic API への追加リクエストが不要。200名のスキャンは数ミリ秒で完了
- **テスト可能**: `scoring.test.ts` が43のテストケースで重み・境界値・類似度行列を検証している
- **透明性**: スコアリング重みの変更がコードの差分として現れ、PR レビューで人間が検証できる
- **ハルシネーション排除**: LLM が訓練データに引きずられて同じ人物（ナポレオン等）を返す「人気バイアス」が構造的に発生しない

## 結果・トレードオフ

**良い点:**
- 43テストが全パスしている（`npm test`）
- 重みの変更が diff として可視化される
- Stage 2 に API タイムアウトリスクがない

**トレードオフ:**
- 類似度行列（`feature-similarity.ts`）は経験則で手動設定しており、統計的最適化はしていない
- 8軸の重みが現在均等（各10点）であり、眼の形と顔の輪郭が同じウェイトになっている
- データセットの人物を増やすほど計算量は O(n) で増加するが、現状の200名では無視できる

## 検討した代替案

| 案 | 却下理由 |
|----|---------|
| LLM に人物選定を任せる | 人気バイアス・再現性欠如・コスト増・テスト不能 |
| コサイン類似度（ベクトル埋め込み）| 埋め込みモデルの追加導入コストが高く、8次元の特徴では過剰 |
| 機械学習モデル（kNN 等）| 訓練データが必要であり、個人プロジェクトの規模に不釣り合い |
| ルールベース（if/else の木構造）| 条件の組み合わせ爆発でメンテナンス不能になる |
